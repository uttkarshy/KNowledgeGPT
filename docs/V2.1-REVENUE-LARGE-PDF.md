# KnowledgeGPT V2.1: first revenue and large PDFs

## Product accounting

- A KnowledgeGPT Credit is a product unit, not a Gemini token.
- Default policy: one credit per answer and one credit per processed document page (one for non-paginated files).
- Existing and newly registered users receive the configurable starter balance once (`STARTER_CREDITS`, default 100).
- `users.credit_balance` is protected by a database check and conditional atomic updates.
- `api_usage_logs` is the immutable credit/usage journal. Unique idempotency keys prevent retry double-charging.
- Actual generation input/output tokens remain recorded separately. Document entries retain page ranges and embedding model metadata.
- A page batch that fails before any provider call is refunded once. After a provider call starts, the batch remains charged because provider cost may have been incurred. Retries reuse the same charge key.

Commercial packs are operator configuration, not source-code pricing:

```env
CREDIT_PACKS={"launch_500":{"credits":500,"amount_paise":19900},"value_1500":{"credits":1500,"amount_paise":49900}}
```

Razorpay order creation remains disabled until its key id/secret are present. Credits are granted only from a signature-verified `payment.captured` webhook after stored amount and INR currency match.

## Large-document behavior

- PDFs support up to the configured `MAX_PDF_PAGES` (default 500), not an unbounded size.
- The browser uploads first, then the API counts pages and returns the approximate credit requirement. Processing starts only after explicit confirmation.
- Extraction and embedding run in `PDF_PAGE_BATCH_SIZE` page windows (default 25).
- Each embedding sub-batch commits before the next provider call.
- `processed_page_count` is advanced only after the complete page window succeeds.
- Retry resumes after the last completed page window and reuses partial chunk checkpoints inside the current window.
- Unique document/chunk indices, checksums, owner/KB fields, and original page numbers preserve idempotency, tenant isolation, and citations.
- Existing worker soft/hard limits bound monopolization; a stopped task remains retryable from durable progress.

## Manual production deployment (do not run blindly)

1. Back up PostgreSQL and record current ECS/task revisions and application image digests.
2. Build immutable backend/frontend images from the reviewed V2.1 commit. Run the complete unit, frontend, PostgreSQL, and migration suites against those exact images.
3. Set non-secret configuration: `STARTER_CREDITS`, `CHAT_CREDITS`, `DOCUMENT_CREDITS_PER_PAGE`, `PDF_PAGE_BATCH_SIZE`, `MAX_PDF_PAGES`, `MAX_CHUNKS_PER_DOCUMENT`, and `CREDIT_PACKS`.
4. Store Razorpay secrets in the existing secret manager. Register the webhook URL `/api/billing/razorpay/webhook`; never place secrets in source or task definitions in plaintext.
5. Put the API/worker into a controlled maintenance window, then run `alembic upgrade head` once. Migration 0007 is additive and backfills existing users with 100 starter credits.
6. Verify migration state with `alembic current`, schema constraints, existing user/document counts, and a sample of balances.
7. Roll out backend first, then Celery worker, then frontend. Do not run an old worker against the new credit-enabled frontend flow.
8. Smoke test as a non-admin user: balance/usage API, a one-page upload estimate/confirmation, processing/citation, one answer, insufficient-credit 402, and retry idempotency.
9. In Razorpay test mode, verify invalid webhook rejection, valid captured-payment grant, duplicate webhook idempotency, and amount mismatch rejection. Enable live credentials only after test-mode evidence is retained.
10. Run the preserved exact-date, monthly top-N, semantic education query, isolation, retry, and citation checks in production-compatible staging.
11. Monitor 402/429/5xx counts, credit journal deltas, negative-balance constraint violations, document progress, worker timeouts, and webhook failures during the canary.
12. Roll back application images if needed. Do not downgrade migration 0007 after live purchases; keep its additive columns/tables and roll forward.
